Timing calibration (frame duration byte → seconds)

Generate a 4-frame test (two colour pairs), time it and record the result. Byte 0 is reserved / unused — the MCU ignores it in JUMP and FADE; keep 50 or 70 for factory-style frames. Byte 1 is the only timing byte: it sets JUMP hold time and the full FADE frame period. Byte 0 tests are kept only to confirm that it has no effect. JUMP and FADE are fitted separately — the Style selector chooses both the test generator and the dataset used for estimates. Measurements are stored in this browser.

Data management

For timing fits, byte 1 values above ~107 wrap around a 16-bit millisecond counter (65.536 s); the fit unwraps them automatically. JUMP uses the fixed model and ignores these settings. Byte 0 is reserved and ignored by the MCU. Use the on/off button to exclude a noisy measurement; points above "max byte" are also excluded.

Camera auto-timing (JUMP and FADE)

Point a camera at one LED. The tool samples the selected region ~60 times per second, detects any colour change and measures the interval automatically — no stopwatch reaction time. For JUMP hold time: set Style = 01 JUMP and What to measure = Frame duration / Hold time (byte 1), generate/apply a 4-frame test, then record the median. For FADE, the same median is the full frame-to-frame interval. Detection follows the Style selector: JUMP locks after each switch until the new colour settles (no double-crossings); FADE uses continuous crossings. MJPEG is recommended: nginx exposes the configured camera stream (CAMERA_URL in .env) at the same-origin URL /camera, which avoids browser CORS restrictions. Webcam access needs HTTPS or localhost.

How to use

  1. Decode / Explore: paste any DP25 hex string (or pick one from the Library) and press Decode. See all 8 fields, colours and animated preview.
  2. Design / Edit: load an existing effect as a template (or start blank), adjust the reserved byte 0, frame duration byte 1, style, hue, saturation, value and white fields, then Copy the generated hex. Save effects with Save current.
  3. To test on hardware: copy the generated hex, then in HA go to Developer Tools → Actions, select script.gledopto_send_raw (supplied YAML) and paste the hex into the value field.
  4. Hypothesis Check: inspect a string field by field and change one value at a time to verify the decoding on real hardware.

Effect string format (experimentally confirmed)

[1 byte] scene ID                00..ff, for example 04 or 1c

[N frames, each 13 bytes]
  [0]     reserved / unused     raw byte; ignored by MCU in JUMP and FADE;
                                kept for the 13-byte Tuya layout, use 50 or 70
  [1]     frame duration        raw byte; the only working timer
                                JUMP: hold time of the static frame
                                FADE: full frame period (transition + hold)
  [2]     style                 00=static, 01=jump, 02=fade, 03=strobe/flash
  [3:5]   hue                   big-endian u16, degrees 0-360
  [5:7]   saturation            big-endian u16, 0-1000 = 0-100%
  [7:9]   value (RGB bri)       big-endian u16, 0-1000 = 0-100%
  [9:11]  white brightness      big-endian u16, 0-1000
  [11:13] white temperature     big-endian u16, 0-1000 (warm to cold)

Timing driven by byte 1:
  JUMP 0..107    (108 - byte) x 0.1035 s       11.18 s .. 0.10 s
  JUMP 108       fast strobe after ~32.7 s startup delay
  JUMP 109..255  uint16_t overflow (65.536 s) 65.43 s .. 50.17 s
  FADE period    (108 - byte) x 0.207 s        about 2x the JUMP time
    byte < 65    ~8.4 s transition + hold until end of period
    65..85       continuous 0% -> 100% ramp, no hold
    86..107      fast overlapping frames with reduced amplitude

Example: 46 46 02 00 78 03 e8 03 e8 00 00 00 00
  reserved byte 0=70, frame duration byte 1=70, fade,
  hue=120 (green), sat=100%, RGB=100%, white off

Evidence that confirmed this layout

  • grassland: frame 2 had 000a at bytes [7:9] → RGB value 1% → dim green. That is why it breathes.
  • reading (white preset): 0e0d ... 03e8 01f4 → white brightness 1000, temperature 500 → bright neutral white.
  • good_night (white preset): 0e0d ... 00c8 0000 → white brightness 200, temperature 0 → dim warm white.
  • Byte roles corrected experimentally: byte 0 is reserved / unused in JUMP and FADE; byte 1 is the only timing byte. In JUMP, byte 0 = 255/128/64/0 all gave the same interval — no measurable effect.
  • Byte 1 in JUMP — fixed model, not a fit: 0..107: (108 − byte) × 0.1035 s → 11.18 s down to 0.10 s. Byte 108 produces a fast strobe (~0.10 s) after a ~32.7 s startup delay. Bytes 109..255 wrap a 16-bit millisecond counter (65.536 s), giving 65.43 s down to 50.17 s.
  • Wrap logic: the counter overflows at byte 109, not 108. Byte 107 flashes rapidly, byte 108 starts the strobe after the startup delay, and byte 109 begins the long ~65 s branch.
  • Byte 1 in FADE: the full frame period is about twice the JUMP time, (108 − byte) × 0.207 s. Byte < 65 gives a ~8.4 s transition followed by a hold; 65–85 gives a continuous 0→100% ramp; 86–107 gives fast overlapping frames with reduced amplitude.
  • Test colours: each generated test uses two colour pairs (for example red↔blue then green↔orange) and rotates them on every Generate, so it is obvious that a newly applied string really took effect.
  • FADE tests (style 02): use the Style selector in Timing calibration. JUMP and FADE measurements are fitted separately. Record both the full interval and (if measurable) only the smooth transition — that separates "how long the colour stays" from "how long the transition takes".
  • Style: 01 = jump (hard switch), 02 = fade (smooth). Confirmed by hardware test.
  • The "soft" and "dynamic" captures are one byte short (55 hex chars); do not use them.
  • All decoding is inferred from captured data and experiments, not from manufacturer documentation. Verify with real hardware.
